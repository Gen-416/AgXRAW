# AgXRAW 产品架构与领域模型

[English](PRODUCT_ARCHITECTURE.md) · [成像管线与技术细节](ARCHITECTURE.zh-CN.md)

> 本文回答“产品由哪些职责、用例和领域对象组成”。它采用表现层、应用层、领域层、
> 基础设施层四层软件架构。现有的[架构与技术细节](ARCHITECTURE.zh-CN.md)回答的是
> “像素依次经过哪些处理阶段”；其中 Capture、Tone、Color geometry、Delivery 是成像
> 管线阶段，不是本文的软件架构层。

![AgXRAW 四层产品架构与领域模型](assets/product-architecture.zh-CN.svg)

## 如何阅读这张图

- 纵向的四个大区域是软件架构层。上层发起用例，下层提供规则或技术能力。
- 采集证据、显影、交付是三个并列的边界上下文，它们全部位于同一个领域层。
- 粗边框表示聚合根；普通框表示领域对象、策略或政策。
- 上下文之间只交换明确的领域契约：采集证据进入显影，完成的成片进入交付。
- 显影计划不是单一参数袋。它分别治理**影调计划**与**色调计划**的决策权。

本文统一用**色调计划**指 Color Plan。它不只是 hue/tint，还拥有色相路径、色度退让、
原色几何与色域适配；影调计划则只拥有亮度关系。两者是职责分治，不代表所有形成算法在
数学上都能拆成两个独立变换。

这套分层首先保护三条产品边界：事实不决定审美，显影不决定封装，编码不反向改变
已经形成的像素。

## 01 表现层

表现层接收人的操作或程序请求，并呈现结果、进度、解释与错误。当前产品提供四种表现能力：

- 本地可视化界面；
- 命令行批处理；
- 程序化调用接口；
- 报告与诊断呈现。

表现层可以校验输入格式和显示状态，但不拥有“证据是否可靠”“显影是否合法”或“交付是否
合格”的规则。不同入口对同一个用例应得到相同的领域结果。

## 02 应用层

应用层组织一次工作会话。它决定调用顺序、收集输入、保存会话状态并传播错误，但不重新
定义领域不变量。

| 用例 | 编排行为 | 领域结果 |
|---|---|---|
| 导入并准备采集 | 接收 RAW/DNG、选择解码能力、建立会话 | 可被分析的采集 |
| 分析采集证据 | 请求传感器与场景测量，汇总诊断 | 采集分析与空间颜色许可 |
| 设定观看与显影意图 | 合并自动结果和显式用户选择 | 显影意图 |
| 编译显影计划 | 把证据与意图交给领域裁决 | 编译完成的只读显影计划 |
| 实时预览与受限调节 | 应用有界偏置并重新形成预览 | 可解释、可复现的预览 |
| 导出 SDR / HDR 成片 | 按所选形成合同生成 SDR 与可选 HDR，再交给交付 | 完成成片集 |
| 生成解释与诊断 | 汇总事实、决策、降级与验证结果 | 报告和错误说明 |

应用层不得把界面默认值偷偷升级为领域规则，也不得绕过显影计划直接拼接渲染参数。

## 03 领域层

领域层是统一语言和业务不变量的唯一归属。三个上下文并列协作，各自拥有不同的事实和
决策权。

### 采集证据上下文

这个上下文回答“传感器记录了什么，以及哪些部分仍然可信”，不回答“照片应该是什么样”。

| 领域对象 | 主要行为 | 不变量 |
|---|---|---|
| **采集（聚合根）** | 持有传感器证据与场景帧；保留解码、标定和几何来源；复用重建结果切换声明白平衡 | 更换场景解码器不能改写证据来源 |
| 采集分析 | 解析满阱、剪切、噪声和动态范围；区分可靠主体、可靠高光尾部与重建区域 | 重建高光不能反向成为传感器证据 |
| 空间颜色许可 | 根据逐像素余量、剪切类别与 SNR 编译颜色路径可用的自由度 | 没有空间证据时不得伪造逐像素 mask |

采集上下文向显影上下文交付的是**证据**，不是审美结论。

### 显影上下文

这个上下文回答“在事实与明确意图的约束下，怎样合法地形成图像”。意图由用户声明，计划由
系统裁决。

| 领域对象 | 主要行为 | 不变量 |
|---|---|---|
| 显影意图 | 声明白平衡、曝光偏置、胶片观察位置、显示目标与显式观看选择；区分自动结果和用户偏置 | 用户偏置不能改写采集事实 |
| **显影计划（聚合根）** | 固化场景度量，分别治理影调与色调决策，并在聚合级校验形成、胶片和输出模式的兼容性 | 编译后按只读合同消费；下游不能重新解释 |
| 影调计划 | 固定曝光锚与 EV0 支点；编译黑白端点、动态范围、趾部、肩部与局部对比；从可靠尾部派生独立 HDR 肩部 | 色彩压力和输出色域不得重编译影调；显示容量只能限制 HDR 峰值并重解 K 以上肩部，不得改写曝光锚、scene white endpoint 或 K 以下主体曲线 |
| 色调计划 | 规划色相路径、色度退让与原色几何；按 CFA 可靠性授予颜色自由度；拟合 SDR gamut 或 HDR color volume | 只能沿既定亮度权威形成颜色，不得重编译曝光锚或影调端点 |
| 显影执行 | 按形成模式合成影调与色调计划；执行 AgX、RAW 门控、仅亮度、中性诊断或胶片接管 | 标准 AgX HDR 从 scene 独立形成；film-full 以完成的胶片印相 SDR 为基图，只在印相参考白以上扩展由 scene 证据支持的高光 |

#### 影调计划与色调计划

两者是同一个显影计划中分别治理的职责，而不是两个架构层，也不是先后覆盖的滤镜：

| | 影调计划 | 色调计划 |
|---|---|---|
| 核心问题 | 场景亮度怎样映射到显示亮度？ | 颜色沿什么路径进入目标显示空间？ |
| 拥有的决策 | 曝光坐标、黑白端点、动态范围、支点、趾肩、局部对比与受显示容量约束的独立 HDR 肩部 | 色相路径、色度退让、原色几何、证据门控的颜色自由度与 SDR/HDR 色域适配 |
| 不拥有的决策 | 色域封装与编码参数 | 影调端点、曝光锚与影调曲线 |
| 实现统一语言 | Tone Compression Plan | Color Geometry Plan |

白平衡属于显影意图和场景帧形成前提；它会影响计划所观察的场景样本，但不会被色调计划
静默改写。胶片与 HDR 都可能同时约束两份子计划，因此由显影计划在聚合级校验形成模式、
胶片模式与 SDR/HDR 兼容性。胶片 full 等联合形成可以同时作用于影调和色调，但仍必须声明
两边各自的决策权与不变量。

当前实现中的 Render Plan 已同时携带 scene、tone、color；启用胶片时还会携带经过校验的
胶片曝光、显影、印相与模拟完成计划。领域合同要求编译完成后按只读方式消费；这描述的是
对象行为边界，不声称所有内部数据结构都已完成物理拆分或深层不可变改造。

因此 HDR 有两份明确的形成合同：标准 AgX HDR 从 scene 独立形成；film-full HDR 以已经完成
的胶片印相 SDR 为主体，只在印相参考白以上叠加由 scene 证据支持的高光扩展，不重新显影
主体，也不把结果声明为物理胶片 HDR。

### 交付上下文

这个上下文回答“怎样把已经形成的像素可靠地交给外部世界”。形成决定像素，交付决定封装。

| 领域对象 | 主要行为 | 不变量 |
|---|---|---|
| **完成成片集（聚合根）** | 持有单一 SDR，或 SDR 基图与 HDR alternate；声明显示余量和输出色域 | 进入编码器前，像素形成已经完成；交付只能读取完成成片 |
| 交付政策 | 选择容器、质量和色度采样；执行原子写入、回读与往返容差验证 | 编码参数不得反馈改变图像形成 |

显影上下文向交付上下文交付的是**完成的成片**，而不是可供编码器重新解释的场景数据。

## 04 基础设施层

基础设施层实现领域需要的技术能力：

- 传感器证据提供；
- 场景解码；
- 原生计算加速；
- 图像与 Gain Map 编码；
- 标定资产提供；
- 本地文件与系统图像服务访问。

基础设施可以更换实现，但不能拥有证据、显影或交付规则。新的解码器只要交付共同的场景
契约就能接入；新的编码器只能消费完成成片，不能反向参与显影。

## 上下文契约

| 契约 | 生产方 | 消费方 | 必须保证 |
|---|---|---|---|
| 采集证据 | 采集证据上下文 | 显影上下文 | 来源、可靠性、空间适用性和降级状态可追溯 |
| 显影计划 | 显影上下文 | 显影执行 | 场景度量、影调计划和色调计划按只读合同消费且不越过各自决策权 |
| 完成成片集 | 显影上下文 | 交付上下文 | 包含单一 SDR 或 SDR/HDR 成片对；像素形成结束，色域与显示余量声明明确 |
| 交付结果 | 交付上下文 | 表现层 / 外部调用方 | 容器、配置、Gain Map、像素误差和失败状态可验证 |

## 扩展判断

新增能力时，可以用以下问题判断它应该落在哪里：

1. 它只改变交互和呈现吗？放在表现层。
2. 它只编排已有规则吗？放在应用层。
3. 它引入新的业务词汇、不变量或裁决权吗？放进相应的领域上下文。
4. 它只是提供解码、计算、编码、存储或标定能力吗？放在基础设施层。
5. 它同时改变影调和色调吗？先声明两边各自的决策权与跨计划约束，再由显影计划在聚合级
   联合校验和执行。

像素级执行顺序、算法公式、SDR/HDR 分支与编码验证细节继续以
[成像管线与技术细节](ARCHITECTURE.zh-CN.md)为准。
