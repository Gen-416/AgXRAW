# 导出重试复用与最终预览：2026-10-05

主图复用、最终预览与 Core Image 回读释放边界已实施；手动／自动 HEIF 固定母版、真实 JPEG CLI、
preset 全帧评估与生产内存检查点验收已完成。参考代码为 `e035771`，优化代码为本批提交所含实现。
测量摘要见 [公共 JSON](../../assets/performance/export-reuse.json)。本记录延续
[2026-09 管线完成记录](performance-pipeline-completion.zh-CN.md)，只登记导出边界的新增变更。

本批减少手动 HDR 辅助图重试时的重复主图编码，以及 GUI 导出后的重复预览编码，
并为 Core Image 的逐次回读建立局部 autorelease 释放边界。
相同母版、质量、采样和编码器设置可复用已编码的主图；新辅助图及每轮完整文件仍各自验收。
24MP 手动 HDR HEIF 对照从 **75.6263 s 降到最终生产版本的 21.3093 s**，主图编码由五次变为一次。
这是触发全部五档辅助精度重试的固定母版测量；初版仅主图复用的结果为 20.8074 s，
随后增加局部回读释放边界。它不代表自动搜索或完整 RAW 管线有同样收益。

## 实施内容与验收合同

`gainmap.py::_write_gainmap_prepared` 为手动 x265 HEIF 创建一次导出内的
`PrimarySearchSession`，临时目录包围整个辅助精度重试过程；手动 JPEG 使用同一只读
prepared base 构造 `PrimaryCodestreamSession`。调用方已经传入 session 时继续使用它，
不接管外部临时目录。HEIF 的 donor 在成功、验收失败和其他异常路径均由本地临时目录清理；
JPEG 的压缩字节只在当前导出内持有。

手动 HEIF 的辅助精度仍按 **95、97、98、99、100** 依次尝试，JPEG 仍为 **95 后可升到 100**。
只在原有 `HdrRoundtripError` 条件下升级；archive、显式辅助精度以及 Apple HEIF 路线保留原规则。
每次重试重新生成辅助图与完整容器，原辅助模板不会被复用到另一精度档位。
相同主图编码请求复用的是压缩 codestream，而不是已通过某轮 HDR 验收的整个文件。

同时修复了旧重试分支丢失 `_primary_session`、`_jpeg_primary_session`、
`_collect_coding_metrics` 与 `_sdr_precheck` 的问题：这些出口本地参数现在随重试继续传入。
默认手动导出仍每轮执行容器检查、SDR 主图读回和绝对误差门禁、HDR 展开读回和完整误差门禁。
外部传入的 precheck 也执行于每一轮；任何非 HDR 门禁失败均直接终止，不会靠降低检查范围继续尝试。

`gui/service.py::run_export` 先选择最终普通 RGB 或带自动曝光文字的 RGB，再生成一次缩略 JPEG。
原流程在开启自动曝光与诊断 PNG 时先生成普通预览，之后又生成标注版并覆盖前者。
最终预览的像素、缩放、ICC、JPEG 编码参数和返回结果保持原定义；交付图及显示指标不受此顺序调整影响。
正常 `return_rgb=True` 路径继续让指标和缩略图共用最终交付文件的回读结果，不新增完整图像缓存。

### Core Image 回读的释放边界

旧版和初版主图复用代码都可能在没有 Cocoa run loop 的连续编码／回读进程中累积 autoreleased
Core Image 对象。仅复用主图编码不能处理这部分逐轮增长。生产入口
`_read_expanded_hdr_rgba_half` 和 `read_primary_rgb_u8` 的 Core Image 分支现在各自建立
`objc.autorelease_pool()`，实际解码在独立 helper 内执行；helper 的原生局部引用结束后再排空 pool。

返回像素继续由 Python bitmap owner 独立持有：HDR 是原有只读 half RGBA 视图，
SDR 内部可借用私有 RGBA owner 的只读 RGB 视图，公开默认仍返回连续 RGB。
排空 pool 不会改变返回像素的可用期、dtype、布局合同或每轮回读与指标计算。
Pillow 的 JPEG 路线在进入 Core Image 分支前返回，不因此引入 PyObjC 依赖。

pool 放在具体回读边界，可同时覆盖自动／手动 HDR、SDR HEIF 以及最终 metadata 后的主图回读。
没有将整个候选或搜索包入大 pool，也没有延长原生图像存储的生命周期或以强制 GC 代替释放合同。
下面的内存诊断实验说明了该方向；正式生产版本的固定母版验收另行登记，不与外部诊断数字混用。

capture metadata 的 best effort 策略、内容签名、最终回读与原子发布继续由既有交付流程负责。
本批没有取消这些门禁，也没有改变默认 AgX、曝光分析、像素尺寸、JPEG/HEIF 质量或自动搜索策略。

## 固定母版基准方法与测量

`tools/benchmark_gainmap_search.py` 新增手动档位入口，可用相同只读 `.npy` 母版测量自动搜索或
手动辅助精度重试。每个版本在独立新进程运行，固定输入哈希、display headroom、主图 quality/chroma、
bit depth、preset 与 tune。计时只包含交付 writer 的搜索或重试，排除模块导入、母版哈希、
capability 暖机与最终文件比对。它也不包含 RAW 解码、分析、AgX 形成、capture metadata 携带和 GUI 响应。

各 trace 记录调用次数、wall time 和扣除同线程嵌套调用后的 self time；嵌套项目不能直接相加，
并发 self time 总和也不是 wall-time 占比。RSS 取交付后的整个测量进程 high-water mark，包含母版加载、
哈希和 capability 暖机，但在最终 artifact 比对之前；这个范围与局部原生平面内存不是同一口径。

测量输入来自 `_SDI0150.DNG` 一次形成后冻结的母版：SDR uint8 `6000×4000×3`，
HDR float16 `6000×4000×4`。环境为 macOS 27.2 arm64、Python 3.14.4、NumPy 2.5.0、ABI 18，
x265 `4.2+1-e444744`，10-bit，`slow` / `ssim`，display capacity 为 3 EV。
母版形成耗时不计入下表。

### 内存检查点：外部诊断与生产 helper

首对的进程峰值 RSS 差异没有在反序复测中重现：参考版第二次约 **2912 MiB**，
仅主图复用的优化版第二次约 **2627 MiB**，不能据首对差异解释为主图缓存造成稳定内存回退。
随后使用外部 `manual_rss_probe.py` 在每轮完成时采样 Mach `task_info` 的 `phys_footprint`，
并分别对回读和整个候选加临时 autorelease pool，定位对象积累的边界。

| 外部诊断方案 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 | 第 5 轮 | 返回后 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 参考版，无 pool | 2915 MiB | 3331 MiB | 3781 MiB | 4227 MiB | 4618 MiB | 4619 MiB |
| 仅主图复用，无 pool | 2913 MiB | 3317 MiB | 3714 MiB | 4104 MiB | 4395 MiB | 4396 MiB |
| 主图复用 + 局部回读 pool 实验 | 2479 MiB | 2511 MiB | 2547 MiB | 2576 MiB | 2819 MiB | 2820 MiB |

这些是特定检查点的**当前 physical footprint**，不是前表的 `getrusage().ru_maxrss` 进程历史峰值。
两者的内存统计范围、计数器和采样时刻不同，不应将各轮 footprint 直接与 peak RSS 相减，
或用返回后的低值替代全过程峰值。
诊断探针还会增加少量 tracing／采样开销，其逐轮时间不与普通基准合并。

局部回读 pool 实验的完整文件、全部交付指标和压缩载荷保持相同。
扩大到整个候选的 pool 实验也通过等价验证，但其第一轮约 **2909 MiB**、返回后约 **2999 MiB**，
且不能统一覆盖独立 SDR／最终回读入口，因此选择具体回读边界。
表内均为**外部诊断实验**，用于选择释放边界；正式 writer 测量见前表。

## 评估但未采用的方案

保留原生 `heif_image` 与其像素平面可省去候选间的重复输入准备，但全尺寸 24MP 的
10-bit / 4:4:4 主图约需 **144 MB** 原生平面，8-bit / 4:4:4 辅助图约需 **72 MB**，
合计额外 **216 MB，约 206 MiB** 长期持有的像素平面容量；这还不包含对象、编码器工作区或已有母版。
这个容量估计不等于完整导出峰值一定增加 216 MB，具体峰值还取决于编码、回读和工作区重叠。

准备阶段探针跳过 libheif 的 HEVC encode／write，但实际执行 context／encoder 创建、参数设置、
有限性检查、128 行 band 量化、逐行复制、NCLX／ICC 附加与清理。
24MP 连续 uint8 → 10-bit 的三次时间为 **73.92、69.53、65.72 ms**，uint8 → 8-bit 为
**35.64、15.56、9.63 ms**。原自动搜索有十次独立主图编码和四次辅助图编码，准备阶段合计不足约一秒，
可省的重复准备部分还小于这一总量；codec 内部颜色转换没有计入可缓存收益。
因此没有延长这些原生输入的生命周期，仍按候选创建并释放。
原始微测为外部 `prepare-cost.json`；它不是完整 x265 编码或整条 RAW 管线测量。

### 既有中档 preset 的全帧评估

初步裁切评估包含已有 `fast`、`medium`、`slow`，随后对同一 24MP 全帧母版验证 `slow` 与 `medium`。
固定主图 **q90 / 4:4:4 / 10-bit / ssim**，x265 pools 为 4，每种模式、每档各一次；
另编码 q95 / slow 参考。HDR 使用同一 Apple aux100 模板，辅助载荷哈希和属性递归比较均相同。
这里改变的是主图 preset，可能改变码流、体积和指标，不属于逐位保持输出的复用优化。

| 模式 | 导出时长：slow → medium | 主图编码：slow → medium | 文件字节数：slow → medium | 体积变化 |
| --- | ---: | ---: | ---: | ---: |
| SDR HEIF | 13.620507 → 8.543934 s | 13.009687 → 7.897508 s | 24,495,918 → 24,786,429 | +1.186% |
| HDR HEIF，同一 aux100 | 16.226501 → 11.062909 s | 14.444817 → 9.123044 s | 55,092,644 → 55,383,155 | +0.527% |

两档均通过生产绝对门禁、相对 q95 / slow 参考的额外误差预算，以及相对同质量 q90 / slow 的额外误差预算。
SDR 与 HDR 主图编码累计从 **27.454504 s 变为 17.020552 s**，本次少约 **38%**，代价是表中小幅体积增长和指标变化。
这是一幅全帧的单次结果，不证明所有场景或批处理都有相同质量与速度收益，也没有全帧验证 `fast`。
默认保持 `slow`，GUI 已有的中档仍可由用户选择；没有用小裁切结果更改默认，也没有把这部分收益计入主图复用。

HEIF metadata 的全文件读取和解析仍保留原门禁。既有 46.25 MB HEIC 的只读轻量测量中，
内容签名热缓存约 20–21 ms，`primary_icc` 约 5.5 ms，收益远小于重复主图编码。
本批没有为了这部分短耗时扩大跨文件缓存或绕过最终签名与回读。
