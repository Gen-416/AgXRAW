# 第一批交付效率改进：主图复用与分阶段验收

基线为 `b110cc2`。本批只优化成像完成后的编码搜索与回读，不改变 RAW 解码、分析、自动曝光、AgX、胶片算法、质量候选、采样或误差门限。

## 改动范围

HDR HEIF/x265 自动搜索在单次导出内复用相同设置的主图编码文件。缓存最多保留当前胜者和当前候选的两个主图文件；参考指标仅保留标量，不缓存十份 decoded。输入 SDR master 在搜索边界复制一次到自有只读存储，防止调用方的可写别名使缓存失效；24MP RGB8 的这份固定副本为 72 MB。本批不宣称降低导出峰值内存，候选完整文件及辅助图模板仍沿用原来的临时目录管理。

同一候选只回读一次 SDR，同时计算原来的 base 和 coding 指标。独立修改 ISO gain map 时，只有最终封装的主图码流、全部关联属性、颜色、几何、关联元数据及可能影响 SDR 的附属图依赖均相同时，才复用该主图的标量指标。未知结构缓存未命中，继续实际回读。缓存命中仍执行该候选的容器检查、base 门限和完整 HDR 验收。

高质量参考仍须完整通过 SDR/HDR 回读。后续候选如果已经超过原 coding 附加误差门限，就提前拒绝，省去必然无法通过的 HDR 重建。门限表由早期和最终检查共用；未执行的 HDR 指标不填零，尝试记录保留实测 SDR 指标和拒绝阶段。搜索顺序、体积规则、相同体积的选择规则及最终发布时点保持不变。

HDR JPEG 和 Apple HEIF fallback 只共享单个候选的 SDR 回读，不套用 x265 主图缓存或 HEIF 分阶段搜索策略。SDR HEIF 的 GUI 返回图复用 metadata 后最终验收得到的像素，消除第三次解码；metadata 后验收本身保留。

## 验证方法

新增 `tools/benchmark_gainmap_search.py`，从固定的完整分辨率 SDR/HDR `.npy` master 开始测量。它记录每个候选、嵌套调用扣除后的阶段时间、编码与回读次数、输入身份、选参、文件大小、完整文件 SHA-256 及压缩 rendition 签名。导入、输入哈希、能力探测和结果比较不计入编码搜索耗时。

```sh
DNGSCAN_FAST=1 python tools/benchmark_gainmap_search.py \
  --base /path/to/hdr-base.npy --hdr /path/to/hdr-alternate.npy \
  --out /path/to/new-output.heic --headroom 3 \
  --reference-report /path/to/baseline.json \
  --reference-file /path/to/baseline.heic --require-match
```

`--require-match` 检查选参、所有候选的接受/拒绝结果、共同数值指标及压缩 rendition 身份。已经提前拒绝的候选可以缺少未计算的 HDR 指标；coding 指标不能缺失。容器字节和大小另行报告，不能把容器重排与成像差异混为一谈。

针对性回归覆盖胜者保留、缓存容量与配置失效、主图/ICC/方向/元数据/附属图变化、未知容器结构、编码失败清理、SDR 提前拒绝、全部候选失败不覆盖旧文件、最终 metadata 后回读和返回像素生命周期。NumPy 与 Rust 都使用原数值定义；本批没有新增 Rust 核。

## 24MP 实测结果

Sigma `_SDI0150`，6000×4000；macOS 27.2 arm64、Python 3.14.4、NumPy 2.5.2、同一份 Rust ABI 14 release 扩展。先测优化版，再在相同环境重测 `b110cc2`；没有并发运行整帧测试或其他大图基准。下表为这对**单样片、单次顺序对照**，不是三次交替测量的中位数，也不代表所有相机的吞吐量。

| 项目 | 原版 | 本批优化 |
|---|---:|---:|
| 编码搜索墙钟 | 291.51 s | 220.80 s |
| 主图编码次数 | 14 | 10 |
| SDR 回读次数 | 28 | 10 |
| HDR 回读次数 | 14 | 7 |
| 独立辅助图编码次数 | 4 | 4 |
| 候选数量 | 14 | 14 |

本次耗时减少 70.71 s，约 **24.3%**。辅助图编码仍约 65 s，是下一阶段需单独测量的主要剩余成本；不能直接降低质量或更换 preset 来冒充本批收益。此前历史基线为 247.18 s，但其辅助图编码耗时仅约 55 s，因此保留作历史记录，不与本批时间混算。

两版的选参、所有候选接受/拒绝结果、候选字节数、全部已计算共同指标均相同。最终均选择主图 **q90 / 4:4:4 / 10bit / slow / ssim**、辅助图 **q80 / 4:4:4 / 8bit**，文件 **46,437,841 bytes**，完整文件 SHA-256 均为：

```text
83bc66cb96e6eb80f4dabf14c46f189b153ea96faaedd124966d66d462196c33
```

压缩 rendition 身份也完全一致；本样例不只是视觉接近，而是文件逐字节相同。七个提前拒绝候选只省略了原版最终同样会拒绝的 HDR 测量，没有补造指标。结构化记录见 [heif-search-reuse.json](../../assets/delivery-quality/heif-search-reuse.json)。

验证记录：完整严格 Rust suite 运行 1,576 项，1,570 通过、6 跳过；最后补齐的缓存身份与集成测试另纳入最终专项。最终 NumPy / 严格 Rust 交付专项各 125 项，均通过、无跳过，含真实的小图 Core Image/HEIF 编码及回读。

后续仍需跨样片及至少三次交替测量建立正式吞吐量基线。本批已完成输出一致性与调用次数验收，不涵盖新的 Rust 核、全候选文件生命周期重构或全管线峰值内存优化。
