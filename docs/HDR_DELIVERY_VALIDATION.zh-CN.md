# HDR 编码回读验证：检查什么，不能保证什么

始于 2026-09-17，更新至 2026-10-09。适用于非胶片 AgX 与共用的 JPEG/HEIC gain-map 写入器；下文有注明阶段与环境的历史测量，不能代替当前出口验收。

## 从数学成像到有损文件

场景线性 Rec.2020 经过共享的曝光、场景修正，分别形成 SDR 与 HDR rendition。
SDR 经 Display P3 输出变换和传递函数后，10-bit HDR HEIF 保留 float32 底图到编码边界；JPEG 与显式 8-bit HEIF 才形成 uint8 底图。HDR 经自身的曲线和色彩体积约束，打包为线性 Display P3 float16 RGBA。
Core Image 根据这两个完成的图像编码 ISO gain map。回读时再将文件里的底图与 gain map 合成为线性 P3，和编码前 HDR 比较。

因此有两个不同的正确性问题：曲线、矩阵、曝光和量化是否计算正确，以及有损容器是否足够保真地保存了计算结果。
Rust 与 NumPy 一致只能验证前一个问题的一部分；两个实现完全一致，也可能共同使用一个不充分的验收指标。

## 原来的盲区

原有检查包括 SDR 码值误差、HDR RGB 相对误差和色品误差。HDR 放行条件使用 8×8 块均值误差及色品误差，逐像素 RGB 相对误差的百分位仅作报告。
容许适量高频损失是有意的：JPEG/HEVC 有损压缩后的像素不可能逐一等于母版。但块均值缺乏对损失幅度的独立约束。

例如灰阶纹理交替为 `0.25, 1.75`，解码全部变成 `1.0`：

- 编码前、解码后，每个 8×8 块的均值都是 `1.0`；
- 两者都是中性色，色品误差为零；
- 原指标的逐像素 p99 相对误差为 `3.0`，却不参与放行。

另一种盲区来自全图百分位：256×256 图像中一个 4×4 高光只有约 0.0244% 的面积；即使彻底消失，p99.9 也可以为零。只检查全图最大 headroom 也不够，画面另一处同样亮的高光可以让最大值维持不变。
这些是验证器反例，不表示真实照片已经发生同样严重的损坏。

独立 SDR HEIF 的 10-bit 路径现已保留完成输出传递函数的 float32 母版，并在编码出口
做一次 10-bit 抖动量化。高精度主图读取使用关闭 HDR 展开的 Core Image RGBAf，颜色转换
的目标是非线性 sRGB 或 Display P3；不能用线性 RGB 直接代替编码器输入。自动候选比较及
元数据搬运后的最终验收均使用浮点回读。误差乘 255 后仍沿用等效 8-bit 码值预算，因此
小于一个 8-bit 码值的差异不会提前消失，也没有放宽原门限。合法解码过冲保留用于度量，
不在检查前裁掉。HDR HEIF 的 10-bit 底图也使用同一浮点回读和误差单位；JPEG 与显式
8-bit HEIF 保留 uint8 合同。HDR alternate 仍由场景浮点分支形成。局部亮度门禁的活动下限仍为八个等效 8-bit 码值，
浮点验收不代表新增了对全部微弱或纯色度纹理的保证。

## 增加的两个指标

令 `Y_e` 是母版亮度、`Y_a` 是解码亮度。亮度由项目 Display P3 的 RGB→XYZ 矩阵 Y 行归一化后计算，与 `output_luma_weights("p3")` 相同。

**块内绝对亮度误差。** 每个 8×8 块 B 计算

```text
L(B) = sum_B(abs(Y_a - Y_e)) / max(sum_B(abs(Y_e)), 0.05 * count(B))
```

报告并检查所有块的 p95，字段为 `block_p95_luma_error`。绝对值在求和之前取得，变亮与变暗无法抵消。上面的纹理反例得到 `0.75`，而不是零。
0.05 的分母下限避免接近黑色的微小绝对误差变成无穷大的相对误差；这与既有 RGB 误差采用同一工程下限。

**局部 HDR 亮度误差。** 在每个块中，选择母版或解码 RGB 任一通道大于 1.0 的像素，记为 H(B)。使用相同公式，仅对 H(B) 求和，再取所有块的最大值，字段为 `highlight_max_luma_error`。
无 HDR 像素的块贡献零。选择两幅图的并集，同时检查高光消失和凭空出现。归一化只使用被选中的像素，不让周围大量暗背景稀释误差，也不让全图面积稀释稀疏高光。

两个新指标都包含不足 8 像素的右边缘和下边缘。Rust 将亮度计算和每块的累计量融合进既有逐像素扫描，使用每 8 列的小型累加器；不增加全分辨率亮度图。NumPy 保留按行分块的独立参考实现。有限性检查、原有块均值与色品门槛继续有效。

24 MP、8 线程、均匀 float16 合成输入，每组 3 次独立进程测量的中位数：新增统计前后，扫描耗时为 0.249 / 0.242 秒，额外峰值内存为 139.92 / 140.34 MiB。耗时在这次短测中基本持平；它不是实际照片的端到端速度测试，不能据此声称整体提速。

## 门槛与实测范围

新增门槛是严重亮度损失的工程上限，不是 ISO 标准规定、视觉无损认证或单像素精确保证。

| 输出档位 | 块内亮度误差 p95 上限 | 局部 HDR 亮度误差最大值上限 |
|---|---:|---:|
| archive JPEG / HEIC | 0.15 | 0.60 |
| share JPEG | 0.25 | 0.85 |
| share HEIC | 0.40 | 0.85 |

验证环境为 macOS 27.2、Apple Silicon、Python 3.14.4、NumPy 2.5.2、原生 Rust ABI 12。
现有 Sigma fp 样张 `_SDI0150`（日光）、`_SDI0199`（高感舞台）、`_SDI0133`（暗光酒吧），全分辨率、EV 0、不启用胶片；分别测试 clip / reconstruct、JPEG / HEIC、archive / share，共 24 个输出组合。
全部通过新增门槛及原有文件检查。下表是每组 6 个组合中的最坏值：

| 输出档位 | 块内亮度误差 p95 | 局部 HDR 亮度误差最大值 |
|---|---:|---:|
| archive JPEG | 0.03776 | 0.14492 |
| archive HEIC | 0.00783 | 0.04755 |
| share JPEG | 0.05084 | 0.70803 |
| share HEIC | 0.03167 | 0.68629 |

share 的局部最坏误差显著高于全图指标，说明均值良好不能等同于每一处高光良好。局部门槛为这类有损编码保留余量，同时拒绝测试中 `4.0 → 0.18` 的高光损失（约 0.955）。这组三张同机样张不能代表所有相机、噪声、光源和系统编码器版本；新增测试保证反例被识别，不承诺所有局部损伤均被检测。

## 采样参数与文件发布

HDR 主图已从 Core Image 模板中独立编码，JPEG 与 libheif/x265 HEIF 可以独立指定 quality 和 420/422/444；主图替换保留 ISO 辅助图及 rendition 关系。Apple-only 路径仍受系统实际输出采样约束，不能仅依据请求参数宣称成功。

编码后必须从实际 JPEG/HEIC 检查采样格式，不能只相信参数推导；运行时行为与预期不符则报错。所有门禁在临时文件上执行，失败不替换已有目标文件，并清理临时文件。新增统计需要 Rust ABI 12，旧扩展不会被当作提供了这些统计而继续使用。

EXIF/XMP 搬运在编码门禁之后进行，因此同样有最终一致性检查：JPEG 的量化表、压缩图像、ICC、ISO 辅助数据保持不变；HEIF 的图像与 tmap 载荷、解码/颜色属性及 rendition 引用关系保持不变，允许 item ID 重排和无效果的零旋转属性移除。元数据改写若改变这些内容，丢弃改写副本，保留此前已验证的成片。另检查尺寸、位深、gain-map 尺寸与声明 headroom；不能以“仍有 gain map”代替内容一致性。HEIF 的 `imir=0` 仍是镜像，不属于零变换，主图替换会拒绝尚未显式处理的镜像属性。

独立主图编码的最高质量参考若未通过 HDR 重建检查，自动策略先将 gain map 的模板编码精度从 95 提高到 100，再建立参考；随后的全部主图候选共用这份模板。手动主图质量也可触发同样的辅助图重试，主图质量与采样不变。此举不放宽任何门禁，也不改变 HDR rendition；返回的 `gainmap_encoding_quality` 记录实际辅助图设置。真实 `_SDI0150` 的最新管线测试中，系统 HEIF 与 x265 在低精度辅助图下均丢失局部高光，局部最大亮度误差约 1.55–1.58；辅助图精度升高后为 0.047，原门禁即可通过。代价是文件可能明显增大，不能承诺 HDR HEIF 一定比 JPEG 小。

本次全量回归：Rust 与 NumPy 模式各发现 1456 项测试，分别跳过 38 / 77 项，其余通过；另在可访问 Core Image GPU 的环境运行 78 项相关测试，无跳过、全部通过。上述 24 个真实输出也以最终配置、全部校验开启的写入器重新编码并通过。旋转暗角、采样冲突、纹理消失、稀疏高光损坏及失败时保留原文件均有回归覆盖。

相关代码：`dngscan/gainmap.py`、`dngscan/delivery.py`、`rust/src/metrics.rs`。回归测试：`tests/test_hdr_delivery.py`、`tests/test_delivery.py`、`tests/test_rust_pipeline_memory.py`。

## 自动编码（2026-09-18）

默认 JPEG 自动选择范围为 q95–q99，以其中最高质量且通过检查的候选为参考，至少节省 5% 才采用更小文件。每个 HDR 候选都先通过本文的绝对门禁，再与同一成片的参考回读误差比较；没有取消或放宽既有门禁。全部候选失败时导出失败并保留旧文件。JPEG 主图已经独立编码，HDR 也能指定 420/422/444。可调 HEIF 使用 x265，支持 8/10-bit 与三种采样，自动从 95、92、90、87、85、82、80 选择。新的主图替换必须保留辅助图数据并重建 MPF/HEIF 地址，正式输出仍通过本文全部绝对门禁。局部 HDR MAE 的候选比较设置 0.04 参考白下限，避免接近零的基线误差把正常压缩误差放大成过严的相对限制；最坏高光与色度预算仍生效。详见 [180 个全尺寸编码实测](DELIVERY_QUALITY_STUDY.zh-CN.md)。

额外比较使用代码域 JPEG Y 的 RMSE、R−Y/B−Y 的 RMSE、8×8 块内绝对 Y 误差 p99；HDR 再比较块内亮度误差、局部高光误差和像素色品误差。精确预算在 `dngscan/auto_encode.py`，不属于 ISO 规范或感知无损保证。编码选择复用完成的 SDR/HDR 图像，不重新计算曝光或 AgX。

## 局部亮度纹理门禁（2026-10-09）

原有全图百分位和块均值仍可能漏过小面积、低于参考白的纹理消失。新增检查覆盖暗部与中间调，在母版与回读图像的相同位置比较有符号亮度差分，距离为 1、2、4、8 像素。SDR 使用现有代码域 JPEG Y 权重；HDR 使用线性 Display P3 的物理 Y 权重。

设母版和回读差分为 `de`、`da`，每个位置的系数损失为：

```text
c = min(abs(da-de) / max(abs(de), f), 1) * min(abs(de)/f, 1)
SDR: f = 8 codes
HDR: m = (abs(Ye(p)) + abs(Ye(p+delta))) / 2
     f = max(0.01, 0.08*m, (8/255)*(2.4/1.055)*sqrt(m))
```

HDR 的第三项将 SDR 的 8 码值预算映射到线性域。sRGB 逆传递函数在非 toe 段的导数给出系数 `(8/255)*(2.4/1.055)*m^(7/12)`；在 `0<m<1` 使用 `sqrt(m)` 作为保守上界，`m>=1` 时既有 `0.08*m` 项已更大，toe 则由 0.01 下限覆盖。这是量化误差的工程预算，不是传感器噪声或视觉可见性的估计。实拍反例中，低精度辅助图仍被拒绝，提升辅助图精度后的正常输出可以通过；暗部、中间调、高光的整块纹理抹除仍得到损失 1。

参考活动度权重避免把平坦区域中新生成的量化振铃误称为原有细节丢失。每个尺度先在同一位置合并水平与垂直方向，再计算每个 8×8 块中最大的 16 个系数损失的平均值；右、下不足一块的位置补零，分母仍为 16。最终取所有块、所有尺度的最大值。因此正负误差不能抵消，单个坏点也不能冒充具有空间支撑的纹理损失。

SDR 字段为 `base_local_detail_loss` / `coding_local_detail_loss`，HDR 为 `local_detail_loss`。所有交付档的绝对上限为 0.90；自动搜索另外与高质量参考比较，上限为 `max(0.35, reference*1.10+0.03)`。这是最坏标量之间的比较，并非逐位置比较两份损失图。缺测、非法输入或非有限计算拒绝通过；alpha 不参与计算。

JPEG 手动导出现在也执行像素回读与这项门禁。SDR HEIF、HDR 主图和展开的 HDR、自动搜索、缓存回读指标都走同一检查；失败保留原目标文件。Rust ABI 20 提供固定大小临时缓冲的原生扫描，NumPy 保留独立分块参考。

这项检查修复的是**局部亮度纹理**覆盖缺口，不是噪声估计器，也不能证明弱纹理或全部颜色细节完整。4:2:0 本身不保留单像素色度变化，实拍显示逐位置 RGB 损失检查还会误拒绝正常共享输出，因此本轮没有加入未经验证的局部色度门禁。颜色保真继续受原有像素色品、块色差和编码色度 RMSE 预算约束；这些指标仍可能漏过小面积、等亮度的颜色纹理损失。

回归覆盖小面积 8×8 / 16×16 / 32×32 亮度纹理、暗部与中间调、多个频率、相位反转、同方差但不相关的替代噪声、奇数边缘、坏点、非连续数组、非有限数据及发布失败时的原子性。具体实拍与性能数值以本轮验证记录为准，不用历史 ABI 12 的测量代替新检查的成本。

同轮实拍验收还修正了旧版本的 headroom 属性读取：当前 macOS 27.2 对有效 ISO 文件不一定在主图属性中返回 `Headroom`。检查器优先读取 ImageIO `DerivationDetails` 的明确线性 `TonemapBaseHDRHeadroom` / `TonemapAlternateHDRHeadroom` 声明；缺少完整声明时，才取 auxiliary HDRToneMap metadata 的 log2 值并换算。旧主图 `Headroom` 仍可读取，已有声明之间不得冲突。SDR base 必须接近 1，HDR alternate 必须更大，非法、非有限、不完整或缺失的 HDR 声明报错；普通无 gain map 的 SDR 文件才保留 headroom=1 的无声明状态。

这里读取的是文件声明，绝不用展开像素的最大值推定 metadata。正常候选也不为两个标量取回整幅辅助图；少见的 auxiliary 后备读取有局部 autorelease pool。全分辨率实拍、完整 clip 缓冲对照以及新增指标的三次独立扫描计时见[验收记录](assets/delivery-quality/pipeline-repair-20261009.json)。

冻结源码的本轮全量回归各发现 1535 项：NumPy 1469 通过 / 66 跳过，严格 Rust 1500 通过 / 35 跳过，跳过不计为通过；Rust 单元测试另有 17 项通过。75 个原生边界探针全部通过，与 NumPy 的局部指标最大差为 `5.96e-8`。24 MP、每组 3 次独立进程扫描的中位耗时，SDR NumPy / Rust 为 0.562 / 0.103 秒，HDR half 为 0.662 / 0.161 秒；这些数值只描述新增检查，不代表端到端导出速度。

三张 fp 样张以自动曝光、AgX、Display P3、800-nit HDR 容量且无胶片处理，分别验收 `clip` / `reconstruct` 下 JPEG 95/420、97/420、100/444、SDR HEIF 95/420、HDR JPEG 95/420 和 HDR HEIF 95/420，共 36 个全尺寸输出，全部通过；日光样张的四条自动 SDR/HDR JPEG/HEIF 路径也通过。p99.99 使用量与文件声明的真实峰值分开记录，不能把使用量当成正式导出的硬上限。三张 `clip` 的完整 scene 缓冲和尺度与基准一致，但新增解码边界置信度可能影响最终 SDR/HDR 成像。高精度辅助 gain map 可显著增大 HDR 文件，不能承诺这些容器都在 20 MB 内。这份历史验收时仍使用 8-bit SDR 母版；后续真正的 10-bit SDR 与 HDR HEIF 底图改动见[管线复核记录第 13、14 节](reviews/NOISE_TEXTURE_RESEARCH_2026-10-09.zh-CN.md)。
